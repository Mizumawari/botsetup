# アプリケーションに「意図的に入れる」表現技術

普通の UI 部品を並べるだけでは入ってこないものがあります。3D 表現、シェーダ、キャラクターの動き、状態と見た目の対応づけ。これらは、意図的に選んで設計しないと、アプリケーションには入らない部分です。Bot オフィス（状態可視化ダッシュボード）の制作で得た知見をまとめます。

## 目的が先、表現は後

- 見た目の楽しさ自体が目的ではなく、「ボードや状態ファイルを見に行かなくても、異常と判断待ちが目に入る」ことが目的
- 表現の良し悪しは、この目的に効いているかで測る。派手でも、状態が読み取れなければ失敗

## three.js を使う、という選択

- ライブラリは CDN＋ES Modules（importmap）で読み、ビルド工程なしにする。静的配信でもローカルでも開ける形を保つと、運用の置き場所を選ばない
- 画面はアイソメトリックな小さな 3D オフィス。登場人物（Bot）ごとにデスクとアバターを置き、色分けと簡素なローポリで十分に区別できる
- 3D にするのは「状態を空間に置く」と一目で掴めるからで、装飾のためではない。誰がどこで何をしているかが、文章の表より速く読める

## 状態 → 見た目の対応づけ（ここが設計の本体）

- 状態ごとに、頭上のランプ色とアニメーションを対応づける（作業中＝タイピング／歩行、待機＝静止、停止＝赤い点滅、判断待ち＝持ち主の席への吹き出し）
- 名札（名前と現在タスク）は、キャラクターと重ならないよう避けて配置し、必要なら引き出し線で結ぶ
- **鮮度の表現**: 最終イベントからの経過で表示を褪せさせる（段階を分ける）。古いまま放置された状態が、見た目で分かるようにする
- **「記録なし」の表現**: 値が無い（null）場合は、古い状態の褪せ方とは別の印（灰色の輪、点線の名札）で示す。無いものを、もっともらしい見た目で埋めない
- 承認待ちが複数溜まったら、名札の重なりを抑えるなど、混雑時の表現も先に決めておく

## シェーダとトゥーン表現

- フラットなマテリアルのままだと、キャラクターの個体差と「生きて動いている」感じが出ない
- トゥーンシェーディングとアウトライン（輪郭線）をシェーダで入れると、ローポリでも造形が立つ
- キャラクターごとに色だけでなく造形（シルエット）を変えると、遠目でも誰か分かる
- 状態の表情（目が×になる、汗、居眠りなど）も、シェーダとパーツ差し替えで表現できる

## 動きを入れる

- デスク間の移動には経路探索（A* など）を使い、壁や家具を避けて歩かせる。直線移動だと「置物が滑っている」ように見える
- 動きは状態遷移に結びつける（着手したら席を立つ、返却したら運ぶ）。飾りのアニメーションと、意味のあるアニメーションは分ける

## 描画予算と測定

- 予算を先に決める： 描画コール 100 未満、通常のノート PC で 30fps 以上、を目安に置く
- 同じ形の繰り返しはインスタンシング（MultiMesh 等）でまとめると、数千プリミティブでも成立する
- **測定環境の罠**: GPU のない仮想環境（ソフトウェアレンダリング）では fps が一桁台で頭打ちになることがある。これは実機の予測にはならない。描画の可否は実機で測り、仮想環境の数字は「動く／動かない」の確認に留める
- レンダラの違い（互換モードと高機能モード）で、フォグやグロー（発光）の見え方が変わる。どちらのモードで出すかは、実機で見比べて決める

## 意図的に入れる、の判断基準

次に当たれば、表現技術へ投資する価値があります。

- 状態の種類が多く、表やリストでは異常が埋もれる
- 見る人が毎日開く画面で、開く理由（異常と判断待ちの検知）を速く果たしたい
- 登場する主体（Bot やキャラクター）に個体識別が要る

逆に、一度だけ使う管理画面や、正確な数値の読み取りが主目的の画面では、表現より情報の正確さと密度を優先します。
