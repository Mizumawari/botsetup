# 共有ブレイン（secondbrain）の設計

複数の Bot が共有する知識置き場の設計です。発想の元は「Claude Second Brain 2.0」という4層モデルの記事で、それを単一の AI ではなく「Bot 群の共有脳」に読み替えました。

## なぜ要るか

- Bot ごとに文脈が閉じると、持ち主が同じ説明を何度もすることになる
- チャットで伝えただけの指示は、会話の圧縮やセッションの切替で消える。ファイルに書いたものは読み直される
- 決定の理由が残らないと、後から来た Bot が同じ議論を蒸し返す

## 4つの層

知識は「必要なときだけ読み込まれる層」に置くのが原則です。地図を小さく、中身を大きく保てます。

| 層 | 置くもの | いつ読まれるか |
|---|---|---|
| 1. 地図 | 全体の目次（100行以内に保つ）。現在地を示す「いま」のファイル | 毎回 |
| 2. ルール | フォルダごとの書き方（パスで効く範囲を絞る） | そのフォルダを読み書きするときだけ |
| 3. 手順 | 仕事ごとの手順書（playbooks） | その仕事のときだけ |
| 4. 日記 | 各 Bot の日記（教わった・直された・気づいた） | 書くのは各 Bot。定期巡回で昇格判定 |

構成のイメージ:

```text
BRAIN.md          … 地図（目次）。ここから必要なファイルだけを開く
projects/         … プロジェクトごとの状態と次の一手（now.md が現在地）
people/           … 人と Bot のカード（役割、渡し方）
notes/            … トピックごとの事実。1ファイル1トピック
decisions.md      … 決定の記録（何を、なぜ決めたか。過去分は書き換えない）
diary/            … Bot ごとの日記
playbooks/        … 手順書
.claude/rules/    … フォルダごとの書き方ルール
scripts/          … 機械チェック
```

## 使い方（各 Bot の手元での持ち方）

- 基本形は「repo を自分の環境に落として（clone）、手元で読み書きし、push できる Bot は時折 push する」です。常時接続や共同編集の仕組みは要りません
- 作業の開始時に最新を取り込み（pull）、地図と「いま」を読む。作業中の更新は手元の複製に対して行う
- push の経路は2つあります：
  - 直接 push できる Bot：日記のような追記は main へ直接、地図や決定のような重要ファイルはブランチ＋PR（検証役が確認してから取り込む）
  - push できない Bot（アカウント権限がない、実行環境が限られる）：窓口の Bot（まとめ役）に渡し、その Bot が代わりに書き込む
- 人間が自分でブランチを切って使う場合は、普通の repo としてそのまま使えます。取り込み時のルール（重要ファイルは PR）は、複数 Bot で使う場合の事故防止で、一人で使う分には緩めて構いません
- 公開 repo（この botsetup のような形）なら、アカウントがなくても clone して読めます。書く側だけ、アカウントと権限が要ります。非公開 repo は、読むにも権限が要ります

## 運用ルール（要点）

- 作業の前に、地図と「いま」を見て、関係するファイルだけを開く。全部を毎回読まない
- 判断の根拠にしたら、使ったファイル名を挙げる。載っていないことは「載っていない」と言い、推測で埋めない
- 日記はそのままでは共有知識にしない。定期巡回で読み、全体に効く学びだけを notes や decisions へ昇格させる（昇格は4択で判定する：昇格する／プロジェクト側に残す／決定として記録する／昇格しない）
- 決定の変更は、過去の記録を書き換えず、新しい決定として積む
- 読みは全 Bot、書きは権限を持つ Bot だけ。配下の Bot の追記は窓口が集約して入れる
- 共有しないメモ（各 Bot の手元だけに置くもの）は、共有リポジトリに入れない層を分ける

## 文章だけでは守られない

地図やルールの文章は「参考情報」として読まれるだけで、強制力はありません。必ず守らせたいものは、文章ではなく仕組みで止めます。

この設計では、機械チェック（スクリプト＋CI）が次を毎回確かめます。

- 地図の行数が上限を超えていないか
- ファイル名の形式がそろっているか
- 秘密情報らしき文字列が混ざっていないか
- リポジトリ内の相対リンクが壊れていないか

## 合わせて使う仕組み

- **受け渡しの型**: 依頼 → 返却 → 検証済み、の3フォルダで状態を表す。機械可読な台帳（JSON）を正とし、人間向けの一覧表はそれに従属させる
- **台帳の整合チェック**: 一覧表・依頼ファイル・台帳のずれを検出するチェックを別に用意し、「契約違反」と「人間向けファイルとのずれ」を分けて出す（どちらを正とするかは機械が決めない）
- **承認センター**: 持ち主の判断が要るものだけをカードで並べ、ボタンで決められる形にする。議論が要るものはカードにしない
- **判定レイヤー**: 作るのは LLM、選ぶ・測る・通すのは判定（選択／スコア／可否＋確信度、渡すのは証拠だけ）、実行は手順とコード、不可逆な操作は承認ゲート、という分離
- **週次見直し**: 矛盾・古さ・重複を定期的に潰す。ファイル同士が食い違うと、どちらかが任意に選ばれうるため

## 始めるなら

1. 地図1枚と、プロジェクトの「いま」だけから始める
2. 書き方ルールは、実際に読み書きするフォルダが増えてから足す
3. 機械チェックは最初から入れる（行数・ファイル名・秘密情報・リンク切れの4点で十分）
4. 日記は「書く」より先に「昇格の判定」を決める。昇格先がない日記は溜まるだけになる

## 単一の AI だけで使う場合の読み替え

この設計は複数 Bot のためだけのものではありません。単一の AI エージェント（例：Muse 一つ）でも、層の考え方はそのまま使えます。

| 層 | 単一の AI では |
|---|---|
| 地図 | 長期メモリ／ユーザー情報のファイル（毎回読むもの。小さく保つ） |
| ルール | 運用ルールのファイル（作業の進め方、禁止事項） |
| 手順 | スキル／プレイブック（仕事の種類ごとに） |
| 日記 | 日次記録（セッションをまたぐ学びを残し、効くものだけ上の層へ昇格） |

共有リポジトリである必要はなく、一つの作業フォルダの中に層を持てば十分です。複数体制との差が出るのは次の点です。

- **検証の独立性が弱くなる**: 作る側と測る側が同一になる。代替策として、検証は別セッションや時間を空けて行う、期待値を先にファイルへ書いてから実行する、機械チェックと固定条件の実測に寄せる
- **文脈の持ち主が一人になる**: Bot 間の受け渡し（依頼→返却→検証済み）の型は、「過去の自分への受け渡し」として残すと、セッションが替わっても状態が追える
