# 自己改善ループと資産ライフサイクル — 直して、測って、捨てる

Bot の運用は、入れた仕組みの数では良くなりません。効いたかどうかを測り、効かないものを捨てるところまで回して初めて良くなります。このドキュメントは、エージェント自身の運用を改善対象として扱うための型をまとめます。

前提は2つです。

- **改善はファイルの書き換えで起きる**。チャット上の「改善しました」という宣言は改善に数えない。実ファイルに反映され、読み戻して残っていることが完了条件
- **反映と効果測定は別物**。反映は手段であり、効果が観測されて初めて改善と数える

## 1. 改善ログと閉ループ

指摘・事故・違和感が起きたら、その場で改善ログに登録します。持ち帰って後で書くと、事例の半分は消えます。

登録の形式は「事例／原因／対策／反映先／回帰チェック／次に測る機会／状態」です。

- **原因**は「なぜ」で一段深く掘る。表層のままだと対策が場当たりになる
- **対策は失敗の型の水準で書く**。「ツール X で起きたから X 用の注意を足す」ではなく、「片側の情報だけで状態を断定した」のような型で書く。型で書けない場合は、一般化できない理由を併記する
- **回帰チェック**は、各事例に1つ、観測可能な合否の形で付ける。対策文の言い換えではなく「観測する事実」を書く
- **状態**は正直に付ける。効果が測れていないものは「効果未測定」と明示し、成功とも失敗とも数えない。同型の事象が再発したら「差し戻し」として数える

ループは「登録 → 型への一般化 → 実ファイルへの反映（読み戻し確認）→ 次の機会での効果測定 → 定着、または差し戻し」です。

### 較正指標

週次で次の3点を記録すると、改善の仕組み自体の健康状態が見えます。

- **較正比率**: 報告した完了数に対して、痕跡（ファイルの実状態・実行記録・読み戻し）で確認できた完了数の比。自己申告の過大さを見る
- **first-detector 比率**: 問題の第一発見者の内訳（エージェント自身／定期ジョブ／利用者）。検出が利用者の指摘に寄っている状態は、仕組みの欠陥として扱う
- **差し戻し件数**: 検証で差し戻された判定の件数。判定の甘さを見る

### Hard Case Buffer

その場で直せない違和感・保留は、無理に対策へ変換せず、正式な一段階として buffer に積みます。各項目には登録日、文脈、直せない理由、関連する事例、状態を持たせ、週次で掘り起こします。「保留」がチャットや記憶に散らばるのが一番の放置の形です。

## 2. 資産ライフサイクルと退役

原則・スキル・定期ジョブ・フック・台帳といった運用の仕組み自体も、保守対象の資産です。資産台帳で棚卸し対象にし、外部手法などの採用候補は採用台帳で管理します。

- 候補ごとに「判断／状態／試行の範囲と期間／効果判定の方法／次回判定日」を持つ
- 試行は範囲と期間を区切って（bounded に）行い、判定は**コスト込み**で行う。収穫だけ数えてコストを記録しない判定は未完として扱う
- 判定の出口は必ず「使用継続／改良／統合／整理／退役」のどれかにする。状態遷移なしに宙に浮いた項目を残さない
- 2回連続でコストに見合う収穫がゼロの項目は、縮小または退役の提案対象にする。プラットフォーム側の更新で冗長になった仕組みも退役の対象
- 統合の判定では重複を機械的に敵視しない。原則とスキルのような階層的な重複は、片方を消すより現状維持が正しい場合がある
- 追記型コンテンツの整理は「知識の抽出 → 圧縮・アーカイブ → 要約と参照の保持」の順。自動では何も消さない（削除は人間の判断を介する）

## 3. 定期ジョブの暴走ガード

定期実行には、暴走したときに止まる上限を最初から併設します。

- run 単位の時間上限
- 同一ツール・同一入力の反復上限（目安を決めておく）
- 日単位の上限（実行回数、外部送信回数、消費枠など）。上限を超えたら停止して報告する

停止条件も同じです。「基盤が壊れているときに代替手段で続行する」判断をその場で緩めない。止まると決めた条件では、台帳や報告に何も残さず止まるのが正しい動作です。

## 4. スキル化パイプライン

繰り返し現れる作業や、壁を突破した手順は、正式なスキルに上げる前に「候補」として分けて蓄積します。

- 状態は candidate（未検証）／ verified（検証通過）／ promoted（昇格済み）／ retired（状態として残す）
- 候補の生成はイベント駆動: 同種タスクの2回目、条件分岐を含む複数ステップの手順の解決、壁の突破、訂正後の成功、のいずれかで自動的に候補化する。失敗だけでなく通常の成功も入力にする
- **検証ゲートが中核**。候補は次回同種タスクの発生時に、新鮮な文脈の分身へ「タスク＋候補だけ」を渡して実行・判定させる。生成時の文脈・会話履歴・正解は渡さない（検証の独立性）
- 検証の記録（trace）にリンクしないスキルは、常時読み込みの対象にしない

## 5. 正本配置の監査

長い会話ではコンテキストが圧縮され、恒常指示の一部が落ちることがあります。効いているはずの指示を逆引きして監査します。

- 恒常指示を一覧化し、「その指示が圧縮で落ちていたら、事故・手戻り・利用者の再指示になっていたか」で各指示を判定する
- 重要な指示は、圧縮で落ちない配置（再注入される正本、作業開始時に読み直すファイル）にあることを確認する
- 決定が記録に留まって正本の本文へ反映されていない「未反映」は、この監査で拾う

## 単一の AI だけで使う場合

- 改善ログと閉ループ、暴走ガード、正本配置の監査は、そのまま単独でも使えます
- スキル化パイプラインの検証ゲートは、「新鮮な文脈の分身」が前提です。分身が作れない環境では、時間を置いて素読みで再実行するなど、生成時の文脈から離す工夫で代替します
- 資産台帳・採用台帳は、スキルと定期ジョブの一覧に「次回判定日」の列を足すだけでも始められます

## 段階導入の目安

全部を一度に入れると、どの仕組みが効いたのか測れなくなります。土台（台帳の置き場）→ 改善ログと反映の完了条件 → 効果測定と較正指標 → ライフサイクルの状態遷移 → 高度な機構（検証ゲート、正本配置の監査）の順に、各段階を bounded な試行として入れ、判定日ごとに続けるかどうかを決めるのが安全です。
