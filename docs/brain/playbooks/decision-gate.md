# 手順: 判定レイヤーの使い方

いつ使うか: 作業の流れで「分岐の判断」に当たったとき（振り分け、分類、スコア、進行可否）。誰が: 全 Bot。
背景と問いの型（Choice / Score / Noul）は、判定レイヤー設計（`../../workspace/decision-gate.md`）を参照。

1. その分岐が「文章を書く仕事」ではなく「答えの決まった分かれ道」かを確かめる。書く仕事なら判定は使わない
2. bot-workspace repo の `docs/DECISION-GATE.md` の判定カタログに、その分岐があるか確認する
3. ある場合: state には証拠だけを入れる（終了コード、取得元、本文の抜粋など）。自分の結論は入れない
4. 判定の返り（型つきの答え＋確信度）を受け取る。確信度が下限以上なら、そのまま進める
5. 下限未満、または問い同士の答えが食い違うなら格上げする: 大きなモデル（Muse）に全文を読ませるか、みずまわり に上げる。判定を押し通さない
6. 実行はコードや手順で行い、終わったら本当に起きたかを確かめる（ファイルがある、送信が記録にある、など）
7. 判定の結果と、あとで分かった正解を残す（下限の較正の実例になる。置き場はカタログの指定に従う）
8. カタログにない分岐が繰り返し起きるようなら、カタログへの追加を Muse に提案する。提案には下の形で問いを書いて添える

## 問いの書き方（カタログへの提案の形）

```
分岐の名前: <例: 日記の行き先>
state（証拠）: <何を入れるか。結論は入れない>
問い:
  - Choice <名前>: <選択肢>（それぞれの意味を一文で）
  - Score <名前>: <段階>（低い順）
  - Noul <名前>: <はいの意味を一文で>
下限: <確信度の下限の案。まだ実例がなければ「較正前」>
下限未満のとき: <格上げ先>
```

- 方針は選択肢の説明文に書く。項目名だけで意味が伝わると思わない
- 1つの分岐に問いを詰め込みすぎない（目安 4 問まで）

守ること: 承認ゲート（金銭・公開・アカウント操作・削除）は判定で代用しない。判定の入力に秘密情報を入れない。
外部への投稿（X など）は判定が「安全」と答えても自動で行わない。
