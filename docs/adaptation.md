# 他のアプリケーションへの適応ガイド

この repo の内容は、特定のプロジェクト専用の記録ではなく、別のアプリケーションやプロジェクトを作るときに使い回せる「型」として書いてあります。適応のしかたをまとめます。

## 一般性の3層に分けて読む

| 層 | 中身 | 適応のしかた |
|---|---|---|
| 原則 | 承認ゲート、検証の独立性、記録の残し方、停止条件、取れない値は推測しない | そのまま持ち込む。ドメインに依らない |
| 型（構造） | 受け渡し（依頼→返却→検証済み）、台帳が正・一覧は従属、共有ブレインの4層、巡回による差分検知、ダッシュボードのデータ契約 | 構造はそのまま、名前と置き場所だけ自分のプロジェクトに合わせる |
| 中身 | テーマの種、判定カタログの分岐、キャラクターや画面の表現 | ドメインごとに作り直す。ここが各アプリケーションの個性になる |

迷ったら「これは原則か、型か、中身か」と分けると、持ち込める部分と作り直す部分がはっきりします。

## その前に：作る前に探す（導入前チェック）

「こういうアプリを作りたい」「こうしたい」という要望が出た時点で、いきなり自作に入らないこと。最初に短いチェックを挟むだけで、無駄な自作と作り直しが大きく減ります。

1. **要望を「欲しい結果」に言い換える**：アプリ名やツール名ではなく、結果（何がどうなればいいか）で書く
2. **既存の実物を探して実測する**：GitHub 等で候補を見つけ、実在・保守状況（最終更新）・ライセンスを、取れた値だけで確認する。紹介記事や公称だけで判断しない
3. **3つに分岐する**：既存で足りる → そのまま導入する／簡易なもの → 手元の内部機能だけで済ませる／どちらでもない → 自作する
4. **判断を記録に残す**：「入れない」「自作する」の判断も理由つきで残す。残さないと、同じ調査が数か月後に繰り返される

チェック自体が目的化して本題より長くなるのは逆効果です。短く区切って、分岐だけ決めるのがこの手順の仕事です。

## 適応の手順

1. **主体を洗う**：誰（どの Bot／人）が、何を得意として動くか。単一の AI だけなら、役割を「モード」として分けるだけでも効く
2. **正を決める**：仕事の状態の正（台帳）と、知識の正（ブレイン）の置き場所を先に固定する。後から分けると複写と矛盾が生まれる
3. **受け渡しの型を置く**：依頼・返却・検証済みの3状態と、依頼に必ず含める項目（目的、入力の場所、出力形式、禁止事項、期限の目安）
4. **承認ゲートを引く**：不可逆な操作（お金、公開、アカウント、削除）だけをゲートにする。全部をゲートにすると回らない
5. **トリガーを決める**：最初は手動＋定期巡回の差分検知で十分。webhook やイベント駆動は、契約（ファイルと状態の意味）を変えずに後から速くする
6. **機械チェックを入れる**：台帳の整合、ブレインの形式（行数・ファイル名・秘密情報・リンク）。文章のルールは参考情報にすぎないので、守らせたいものは仕組みで止める
7. **可視化は最後**：状態のデータ契約が固まってから画面を作る。画面から作ると、契約がないまま見た目だけが増える

## 最小構成（これだけで回り始める）

```text
project/
  RULES.md          … 承認ゲートと共通ルール
  requests/ inbox/ outbox/   … 受け渡し
  state/            … 機械可読な台帳（JSON）
  brain/            … 地図1枚＋プロジェクトの「いま」
  tools/            … 整合チェック
```

ダッシュボード、判定レイヤー、承認センターは、運用が回り始めてから足す拡張です。最初から全部は要りません。

依頼・返却・台帳・ブレイン地図の雛形は、この repo の [templates/](../templates/) に置いてあります。ゼロから書かず、コピーして中身を差し替えるところから始められます。

## ドメイン別の置き換え例

| 対象 | 依頼の中身 | 判定カタログに入る分岐 | ゲート |
|---|---|---|---|
| EC の価格調査 | 収集プロファイル、査読依頼 | 同一商品か、在庫適性、価格の歪み | 仕入れ・出品 |
| ゲーム開発 | 実装依頼、計測依頼 | 目標値の達成、互換性の可否、意匠の採否 | 公開・ストア提出 |
| 情報収集リサーチ | テーマの種、候補の検証 | 近さのスコア、一次情報か、宣伝か | 外部への送信・公開 |
| 家庭や個人の用事 | 予約や手続きの代行依頼 | 条件に合うか、空きがあるか | 支払い・確定 |

どのドメインでも、原則と型は共通で、変わるのは「種・カタログ・ゲートの中身」だけです。

## 適応チェックリスト

- [ ] 主体と役割が一枚に書けている
- [ ] 台帳と知識の「正」の置き場所が決まっている
- [ ] 依頼の必須項目（目的・入力・出力・禁止・期限）が固定されている
- [ ] 承認ゲートの対象が不可逆な操作に絞られている
- [ ] 検証する側に、答えの予想を渡さない決まりがある
- [ ] 利用枠・レート制限に当たったときの停止と申告の形がある
- [ ] 機械チェックが1つでも動いている
- [ ] 報告の形式（結論から、数字とリスク付き）が決まっている
- [ ] 新しいものを作る前に、既存で足りないかを一度確認し、判断を記録に残した
