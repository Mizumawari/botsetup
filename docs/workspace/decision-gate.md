# 判定レイヤー設計（JEV 的な仕組み）

2026-11-02 の みずまわり の指示: JEV（TypeSafe AI の判定専用モデル）のような仕組みも入れる。
狙いは、作業の流れの中にある「分岐の判断」を、文章を書く高性能モデルから切り離すこと。

## 1. 三つの仕事を分ける

- **作る**（調べる、書く、計画する）: Muse / Claude 群 / Grok などの LLM が担当
- **選ぶ・測る・通す**（振り分け、スコア、進行可否）: 判定レイヤーが担当する ← ここを新設
- **実行する**（保存、送信、状態更新）: 手順とコード（巡回など）が担当。不可逆な操作は みずまわり の承認ゲート（RULES §1）

LLM が段落で考えて決めていた分岐を、型つきの質問と確信度で返す判定に置き換える。
安く速くなるだけでなく、「なぜそう判断したか」が確信度つきで記録に残る。

## 2. 質問の型は3つだけ

- **Choice**: ラベル付きの選択肢から1つ選ぶ（どの担当か、どの分類か）
- **Score**: 順序のある段階で測る（緊急度、近さ、品質）
- **Noul**: はい/いいえ＋確信度（進めてよいか、承認ゲートに触れるか）

作法（元の記事の要点を、このワークスペースの言葉で）:

- 方針は質問の指示文と選択肢の説明に書く。判定側はフィールド名の意味を推測しない
- 渡すのは「証拠」であって「結論」ではない（例: 終了コード、取得元、本文の抜粋を渡す。「確認済み: true」のような結論は渡さない）

## 3. 確信度と格上げ

- 質問ごとに**確信度の下限**を決める。下限未満なら、大きなモデル（Muse）か みずまわり に格上げする
- 下限は勘で決めず、過去の実例（検証済みの RES、査読の判定など）で較正する
- 判定は速さのためのもので、正確さの保証ではない。不可逆な操作の前には必ず人のゲートを置く

## 4. このワークスペースの判定カタログ

実際に繰り返し起きる分岐を、判定として定義しておく。新しい分岐が定番になったら、ここへ足す。

| 判定 | 使う場面 | 型と選択肢・物差し | state に渡す証拠 | 下限未満のとき |
|---|---|---|---|---|
| 巡回の振り分け | inbox/ に新しい RES が届いた | Choice: 今すぐ検証 / 様子見 / みずまわりへ格上げ。Noul: 承認ゲートに触れるか | RES の要点、対応 REQ の受け入れ基準、差し戻し回数 | Muse が全文を読んで判断 |
| 返却の一次判定 | RES の検証の入口 | Noul: 受け入れ基準を満たす見込みか | 成果物の実在、state の整合結果、基準への対応表 | 通常の全検証に回す |
| 日記の昇格 | secondbrain の diary/ の整理 | Choice: notes へ昇格 / decisions へ記録 / 日記に残す / 古いので破棄 | 追記の本文、日付、関係プロジェクト | Muse が読んで決める |
| 承認の形 | 判断待ちが新たに発生 | Noul: ボタンで決められるか（選択肢が定まり、背景なしで読めるか） | 判断内容、選択肢、影響範囲 | 各チャットで口頭相談に回す（承認センター §4） |
| X 候補の一次選別 | X リサーチの候補が増えた | Score: テーマへの近さ。Choice: 候補 / 隣接 / 対象外。Noul: 一人称の記録か | 投稿サンプル、テーマ種との対応、宣伝の有無 | Muse の検証に回す（独立性は壊さない） |
| 在庫適性の分類 | 輸出 EC 候補の査読 | Choice: A（先に仕入れ） / B（無在庫可） / C（様子見） | 同一商品の確度、ノイズ、価格の安定性、販売元の種別 | 査読で人が読み直す |
| 利用量の警告 | Bot の usage が増えた | Noul: 報告すべき急増か | usage の推移、上限との比 | 管理・Muse が状況を確認 |

## 5. 実装の置き方

- この設計は判定エンジンに依存しない形で書く。質問の定義（型、指示文、選択肢、下限）が資産で、エンジンは後ろで差し替えられる
- 実 Jev を使う場合: 托管 API（自前では動かせない）。利用には TypeSafe のアカウント（または Vercel AI Gateway 経由）が必要で、これはアカウントと課金の話になるため、みずまわり の判断を待つ
- それまでの間（暫定実装）: 基準が明確な判定はルールと小さなモデル呼び出しで代替し、曖昧なものは従来どおり Muse が判断する。カタログと下限の運用は先に回し、較正の材料（実例と結果）を貯める
- vendor の公称値（応答 70–500ms、速度・コストの倍率、価格）は TypeSafe の主張であり、このワークスペースの実測ではない。採用判断は自分の実例での計測で行う

## 6. 守ること

- 判定レイヤーは承認ゲートを迂回しない。金銭・公開・アカウント操作・削除は、判定が何を返しても みずまわり の承認が要る
- 判定の入力に秘密情報を入れない。作業に必要な最小限の抜粋だけを渡す
- 実行の前に進捗を保存し、終わったら結果を確認する（「完了」と言われたことを鵜呑みにしない）
