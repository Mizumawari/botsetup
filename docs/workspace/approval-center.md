# 承認センター設計（Bot オフィス）

2026-11-02 の みずまわり の指示: 全体の仕事の中で「みずまわり が承認しないといけない内容」を
オフィス（Bot オフィス アプリ）で分かりやすくし、ボタンで承認できるようにする。
ボタンで決められないものは、各チャットで口を出す（この文書の §4）。

## 1. 承認アイテムとは

次に当てはまるものだけを承認アイテムとしてオフィスに並べる。何でも並べない。

- 依頼（requests.json）が判断待ち（state=approval）になったもの
- 承認ゲートに触れるもの: 金銭・取引の実行、公開、アカウント操作、削除、方針の変更
- Bot 間の担当や進め方では決められず、オーナーの判断が要るもの

各アイテムには必ず次を付ける（これがないものは登録しない）:
**何を決めるのか（1行）／誰の何のためか／Muse の推奨／承認すると何が起きるか／保留・却下するとどうなるか**。

## 2. ボタンと反映の流れ

- ボタンは3つ: **承認 / 保留 / 却下**。みずまわり がアプリで押す。
- アプリは判断（アイテムID、判断、時刻）を保存する。アプリから repo へ直接は書かない。
- Muse の巡回が保存された判断を読み、repo に反映する（requests / BOARD の更新、
  担当への次アクションの発行）。反映結果はチャットで みずまわり に報告する。
- 承認は「みずまわり 本人がボタンを押した」ことをもって成立する。Bot が代わりに押すことはない。
- 承認ゲート（金銭・公開・削除など）もボタン承認の対象に含めてよいが、
  実行は従来どおり担当が行い、Muse が記録と事後報告をする。

## 3. データの形

- 承認アイテムは repo 側の状態から Muse が登録し、巡回がアプリへ同期する
  （syncstate の拡張として approvals 配列を渡す）。
- アプリ側の判断は getstate 系の読み出しで巡回が回収する（decisions）。
- repo が正。アプリは判断の入力口と表示であり、台帳は repo に残る。

## 4. ボタンにしないもの

- 選択肢がまだ定まっていない、背景説明が要る、感情や関係性が絡むものは、
  承認センターに並べず、関係するチャットで Muse（または担当）が口を出して相談する。
- 迷ったらボタンにしない側に倒す。ボタンは「読めば決められるもの」専用。

## 5. 実装の置き場所

- Bot オフィス アプリ（fullstack）に承認センターのビューを追加する。既存の読み取り専用は、
  この承認センターの範囲でのみ例外とする（ほかの画面は従来どおり読み取り専用）。
- repo 側のダッシュボード（dashboard/）は従来どおり読み取り専用のまま。
