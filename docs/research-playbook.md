# Muse × Grok リサーチ活用術 20選（要約と適用状況）

調べものを始めただけなのに、気づけば一時間。情報は増えたのに、何をするか決まっていない。そうならないために、リサーチを「検索」ではなく「一つの依頼」として設計するまとめです。

出典は、テツメモさんが紹介した Muse と Grok Build の役割分担をはじめとする、X 上の利用報告20件です。各活用法を要点と依頼の型に要約し、私たちの運用への適用状況を付けました。依頼文は運用のひな形であり、すべてを実機で検証したものではありません。料金や無料枠の数字は投稿者の記載です。

## 分担の考え方

- **Muse（司令塔）**: 何を知りたいか、何のために使うかを決め、見つかった情報を整理・比較し、裏取りを経て、企画や判断につながる形にまとめる
- **Grok 側（X 検索担当）**: X 上の投稿を探す。Grok Build は「Muse の実行環境から X 検索を呼び出す経路」、Grok Bot は「複数の Bot や定期実行を含む運用の仕組み」で、別物として理解する
- 共通の型：候補は絞る／出どころを残す／取れない値は推測しない／確認できないものは「未確認」と書く／外部アクション（投稿・購入など）は調査と切り離す

## 20選

### 01 毎朝の情報収集を「読むべき5件」に絞る
大量に出させると、人間の読む仕事が残る。分野を一つ選び、「自分の仕事に関係する最大5件＋選んだ理由」で返すよう指定する。検索できなかった場合は「新情報なし」とせず「X未確認」と残す。
- 依頼の型：「（対象読者）向けに、直近24時間のX投稿を調べて。重要候補を最大5件に絞り、投稿日、投稿者、要点、直接URL、私に関係する理由を付けて」
- 適用状況：**適用済み**（候補の絞り込みと理由付け、未確認の明示を標準にしている）

### 02 速報と確定情報を分けて受け取る
Grok 側には発見を任せ、Muse には情報の状態を整理させる。「公式発表」「本人の利用報告」「第三者の推測」に分ける。同じニュースの転載が十件あっても、根拠が一つなら独立した十件の証拠にはならない。
- 依頼の型：「この新機能についてX上の話題を探して。公式に確認できた内容、利用者の体験談、まだ確認できない情報に分けて。提供開始日、対象地域、対象プランは公式ページと照合し、確認できない欄は未確認と書いて」
- 適用状況：**適用済み**（検証クラスとして、一次情報／利用者モデル／横断パターン／AI仮説を区別している）

### 03 バズ投稿を「自分に使える企画の種」に変える
伸びた投稿を並べるだけでなく、自分の発信とどうつながるかを考えさせる。「作例を見せた投稿」「操作を短く説明した投稿」「失敗と改善を並べた投稿」のように型で分け、自分の題材で検証できる企画案まで出させる。元投稿の文章は流用しない。
- 依頼の型：「反応の多い投稿を5件探して。題材、冒頭の見せ方、説明の順番、読者に与える価値を比較し、私の作例で検証できる企画を3案出して」
- 適用状況：**一部適用**（企画化は用途ごとに実施）

### 04 いいね数だけに頼らず、投稿を比較する
数字の意味は、経過時間、表示回数、発信者の規模で変わる。取得できた数字を同じ項目で並べ、取れない数字は空欄か「取得不可」にし、推定値で埋めない。比率を出す場合も、条件がそろわないものはその違いを表示する。
- 依頼の型：「候補投稿を、投稿日、取得日時、いいね、返信、リポスト、表示回数で比較して。表示回数が取得できた投稿だけ、いいね数÷表示回数を参考値として計算して。取得できない値は推測しないで」
- 適用状況：**適用済み**（取得できた値だけを記録し、取得不可は不明とする基準を共有している）

### 05 Instagram と Threads の伸び方を調べる
接続済みのアカウントから投稿を集め、反応の多い投稿の特徴を分析する。基準（例：200いいね以上）だけでなく、対象ジャンルと期間をそろえることが出発点。取得範囲はアカウントや連携機能に依存する。まず少数の投稿で質と消費量を見てから対象を増やす。
- 依頼の型：「接続済みのInstagramとThreadsで、直近30日の（ジャンル）に関する投稿を、取得できる範囲で調べて。（基準）以上の候補について、テーマ、書き出し、構成、コメントの内容を整理して。件数と検索範囲も明記して」
- 適用状況：**一部適用**（コネクタの範囲で可能。本運用の主対象は X）

### 06 X の話題を Instagram 向けの企画に翻訳する
X で伸びた話題がそのまま Instagram で伸びるとは限らない。媒体をまたぐときは「誰に、何を持ち帰ってもらうか」を先に決め、企画と台本の作成から始める。自分の発信テーマ、読者の知識、過去の題材も渡しておく。
- 依頼の型：「Xで話題になっている（テーマ）を3件探し、初心者向けInstagram投稿の企画にして。各案は、表紙、悩みの説明、操作例、注意点、まとめの5枚構成。元投稿の表現や画像をそのまま使わず、出典と自分で検証する項目を付けて」
- 適用状況：**一部適用**

### 07 競合の発信を複数の SNS で比較する
媒体ごとの役割（短文での訴求、画像での使い方、日々の疑問への回答）は違う。同じ観点で整理してから比較し、最後は「自社が説明できていない疑問」「自社の実例で補える話題」まで落とし込む。
- 依頼の型：「競合3社の公開投稿を直近30日で調べ、XとInstagramの役割を比較して。商品訴求、使い方、実績、顧客への回答の4項目で整理し、各社の代表例とURLを付けて。取得できなかった媒体は明記して」
- 適用状況：**一部適用**

### 08 サービスの評判から、不満の具体的な場面を拾う
「評判がいい？」ではなく、どんな人が、どんな作業で、何に困ったかを拾う。SNS の声は利用者全体を代表しないので、件数で評価を決めず、確認すべき論点を取り出すために使う。
- 依頼の型：「このサービス名と『困る』『使いにくい』『助かった』を含む公開投稿を調べて。利用場面、期待していたこと、実際に起きたこと、投稿者が試した対処を整理して。推測できない項目は不明にして」
- 適用状況：**適用候補**（種リスト方式の調査で同じ型を使える）

### 09 顧客の言葉から、FAQ や説明ページを作る
初心者の疑問を集め、表現の違いを超えて束ねると、説明すべき項目の優先順位が見える。疑問を探す段階では SNS、答えを確定する段階では公式資料、と役割を分ける。
- 依頼の型：「このジャンルの公開投稿から初心者の疑問を集め、料金、初期設定、対応環境、使い方に分類して。繰り返し見つかった疑問をFAQ案にし、回答には公式情報で確認する項目を付けて」
- 適用状況：**一部適用**

### 10 新しいツールを、自分の条件で比較する
比較の前に必要条件（言語、環境、予算、出力形式）を渡すと、話題性だけで候補が増える流れを抑えられる。料金は月額だけでなく、既存契約に含まれるか、追加契約が必要かまで確認する。
- 依頼の型：「候補3サービスを、私の用途である（用途）に絞って比較して。必須機能、連携先、料金、利用上限、出力形式を公式情報で確認し、Xの体験談は補足欄に分けて。最後に試用の順番を提案して」
- 適用状況：**適用済み**（ツール選定では条件先行で比較している）

### 11 買い物や旅行の情報を、一次確認までつなぐ
SNS の投稿は発見の入口。価格や在庫は変わりやすいので、公式の販売画面で確認し、自分の条件（対象日、出発地、税込総額、手荷物条件）に合うものだけを候補にする。確認できないものは参考情報に分ける。購入や予約は調査と切り離す。
- 依頼の型：「希望する旅行先の航空券セールに関する投稿を探して。候補は公式販売画面で確認し、条件に合うものだけを一覧にして。確認できないものは参考情報に分けて」
- 適用状況：**一部適用**（一次確認までつなぐ設計と、購入を切り離す原則を採用）

### 12 定点観測で、前回から変わったことだけ読む
同じテーマを繰り返し調べるなら、前回の結果を基準に、新しく増えた情報だけを取り出す。同じニュースの転載はまとめ、変化がない項目は一行で示す。最初は手動で同じ依頼を繰り返し、条件が固まってから定期化する。
- 依頼の型：「前回の調査結果と比較し、新しい発表、仕様変更、新たな利用報告だけをまとめて。同じニュースの転載はまとめ、前回から変化がない項目は一行で示して。X検索に失敗した場合はX未確認と記録して」
- 適用状況：**適用済み**（差分だけを報告する形を調査方針に明記した）

### 13 週報を「何が起きたか」から「何をするか」へ進める
日々の調査記録が残っていれば、週末のまとめは「試す価値のある動き」「既存作業に影響する変更」「今週は追わなくてよい話題」に分け、各項目に次の行動（小さな検証方法と所要時間の目安）を付ける。
- 依頼の型：「今週の調査記録から、私の業務に関係する動きを3点に整理して。各項目は、起きたこと、仕事への影響、根拠URL、来週試すことの順で書いて。重複する情報は統合して」
- 適用状況：**一部適用**（週次見直しの仕組み自体は共有ブレイン側の運用にある）

### 14 自分専用の調査基準を育てる
自分の仕事、読者、予算、重視する情報源を「調査方針」として一枚に明文化すると、依頼のぶれが減る。保存できる環境なら設定として持ち、そうでなければ毎回添付する設定文でもよい。使ってみて違うと感じたら、検索語より先に基準を直す。
- 依頼の型：「私の調査方針を一枚にまとめて。対象読者は（読者）、優先するのは（優先条件）、予算は（予算）。公式資料を優先し、宣伝だけの投稿は区別して。今後の調査前にこの条件を参照して」
- 適用状況：**適用済み**（テーマの種リスト＋検証基準＋停止条件を一枚の方針に集約した）

### 15 原文と出典を残し、あとから検証できるようにする
重要な情報は、投稿URL、投稿日、取得日時、要点を支える原文の箇所、要約をセットで残す。長文が途中で切れている場合は取れた範囲を全文として扱わず、不足を明記する。引用投稿と引用元の発言は分けて記録する。
- 依頼の型：「採用候補の投稿は元URLを開いて確認して。要点を支える原文の箇所と要約を分けて記録し、長文の末尾が確認できない場合は全文未取得と表示して。引用元がある場合は元の発言までたどって」
- 適用状況：**適用済み**（生の結果をそのまま保存し、要約と分ける）

### 16 画像と動画を、出典付きの資料庫にする
添付メディアも保存し、ファイル名、出典投稿、画像か動画か、引用先のものかどうかを一覧にする。保存の確認は、ファイル数だけでなく、画像が開けるか、動画が再生できるかでも行う（ログイン画面の HTML を画像として保存してしまう事故があるため）。自分の調査用に整理することと、記事へ転載できることは別。
- 依頼の型：「取得できる添付メディアを保存し、ファイル名、出典投稿、画像か動画か、引用先のメディアかどうかを一覧にして。動画は取得できた解像度と長さを記録し、失敗したものは未取得として分けて」
- 適用状況：**一部適用**

### 17 スマホの依頼を、PC で読めるレポートにする
成果物の形（読むためなら PDF、編集するなら文書、再利用するなら Markdown や CSV）と保存先を最初に指定し、ファイル化までを一つの依頼に含める。資料には調査日と対象期間を入れ、URL の一覧を末尾にまとめる。
- 依頼の型：「調査結果を、結論、比較、根拠、次に試すことの順でレポートにして。編集用のテキストと閲覧用PDFを作り、接続済みドライブの指定フォルダに保存して。保存後にファイル名と内容が一致しているか確認して」
- 適用状況：**一部適用**（レポートのファイル化は実施。保存先は運用による）

### 18 利用枠を見ながら、仕事を分担する
全部の作業を一つのエージェントに集めると、利用枠が先に尽きる。X 上の候補探索は Grok 側、整理は Muse、手元の集計は別の処理、と分担の単位を決める。節約の基本は、検索条件をそろえる、重複を除く、取得済みの結果を使うこと。上限やエラーが出たら、その工程を未確認として止める（再試行し続けない）。
- 依頼の型：「今回のX検索は一回にまとめ、結果を保存して再利用して。同じ投稿を繰り返し検索せず、追加調査が必要な理由を示して。利用上限やエラーが出たら、その工程を未確認として止めて」
- 適用状況：**適用済み**（共有プールの枯渇を実地で経験し、停止条件・一回化・結果の再利用を標準にした）

### 19 クラウドの調査を、手元の資料と照合する
外で見つけた情報を、自分の過去資料や作業記録と比べると、重複する題材、新しい視点、更新したい説明が見える。接続構成を増やすこと自体が目的ではなく、差分を見つけることが価値。最初は、必要な資料を調査用フォルダにコピーして渡す方法から始めると範囲を管理しやすい。
- 依頼の型：「渡した過去の企画一覧と、今回の調査結果を比較して。重複する題材、新しく追加できる視点、以前の説明を更新したい箇所を整理して。元ファイルの変更や削除はせず、別のレポートに出して」
- 適用状況：**一部適用**（手元の概念マップとの照合は実施。クラウドから手元 PC へ接続する構成は採っていない）

### 20 調査から制作までを、小さな一周でつなぐ
テーマを決める → 候補を探す → 原文と公式情報を確認する → 比較する → 企画にする → 制作して結果を記録する。この一周を小さく回し、公開後の反応や読者の質問を次の調査条件に戻す。最初は企画や台本までを成果物にしても十分。
- 依頼の型：「今週の（テーマ）を調べ、裏取りできた候補から一本だけ選んで。選定理由、記事の構成、必要な実演素材の一覧を作って。未確認の機能や数字は断定しないで」
- 適用状況：**一部適用**（調査→検証→記録の小さな一周を定期運用で回している）

## 毎回の依頼に入れたい五つの条件

調査を頼む文章は、長ければ優秀になるわけではありません。次の5つが伝われば、かなり具体的な仕事になります。

1. **目的**：何を決めるための調査か
2. **範囲**：期間、対象、媒体
3. **採用条件**：どんな候補を採るか（再現できるか、公式で裏が取れるか、など）
4. **出力形式**：件数、付ける項目（投稿日、投稿者、要約、直接URL、確認できた反応数）、成果物の形
5. **終了条件**：呼び出し回数の上限、失敗したらどうするか、外部アクションの禁止

ひな形：

```text
目的は、（決めたいこと）です。（期間）の（媒体）の投稿から、（採用条件）に合う活用例を最大（件数）件探してください。
X検索にはGrok側のx_searchを使い、呼び出しは今回一回まで。
各候補に、投稿日、投稿者、要約、直接URL、確認できた反応数を付けてください。
重要な機能と料金は公式情報で確かめ、確認できない点は未確認と書いてください。
最後に、（成果物の形）を出してください。投稿などの外部アクションは行わず、検索に失敗したらその状況を記録して終了してください。
```

## 最初の設定は、小さな検索テストから

Grok 側の X 検索を呼べる状態かは、最初に一度だけ確かめます。

1. 導入済みかを確認する。未導入なら、公式の配布元と現在の導入手順を確認し、インストーラの内容を確認してから進める
2. 認証は本人が自分のブラウザで行う
3. 検索を一回だけ行い、返された投稿 URL を一件開いて、内容が一致するか確認する
4. 投稿、返信、いいね、リポストは行わない
5. ログイン名や導入パス、テスト結果を記録しておく（後からの切り分けのため）

初回のテーマは一度に一つ、狭く。「AIの最新情報を全部」ではなく「直近7日の（具体的なテーマ）を5件」。対象が狭いほど、返ってきた情報が役に立つか自分でも確認できます。
